## Bugs

Follow-up from B1/B2 (done, 1.1.9, 2026-10-26): `set_env` now only exports `GOPATH`, so a login shell no longer leaks its inline `DO_*` values into manual runs or nested shells. Anything else a child process needs must be added to the `case` in `set_env`.

- [x] **B1. `--dryrun` is not dry** (1.1.7, 2026-10-26) (`:1316` vs `:1440`). `set_defaults` runs before argument parsing and line 372 resets `DO_DRYRUN`. Confirmed in a sandboxed `$HOME`: `--dryrun` made 108 `defaults write` calls, created dirs, copied `files/`, left the lock file. `--help`/`--version` do the same. `--confirm` is bypassed too. Fix: parse args first, then `set_defaults`, or move `set_osx_*_defaults` into `check_defaults`.
- [x] **B2. `set_env` always overwrites** (1.1.8, 2026-10-26; now unset-only with `force`, uses `typeset -gx`) (`:668-675`). Unconditional `eval export`, so the documented override does not work, and `set_inline_defaults` resets flags set earlier. Fix: return if already set, add an always-override list, use `typeset -gx` instead of `eval`.
- [x] **B3. Prompt and brew env never applied** (1.2.0, 2026-10-26) (`:853`, `:1098`, `:1131`, `:1137`). `oh-my-posh init zsh` and `brew shellenv` output is discarded. Fix: `eval "$(...)"`.
- [x] **B4. Lock leaks on early exit** (1.2.1, 2026-10-26) (`:1470`, `:1501`, `:1508`, `:1529`, `:1545`). `exit` while holding the lock blocks installs for 10 minutes. Check-then-touch (`:139-151`) is racy. Fix: acquire with `mkdir` after arg parsing, release in a `trap ... EXIT`.
- [x] **B5. `files/defaults/macos.defaults` does not exist** (1.2.2, 2026-10-26) (`:332-334`, `:926`). `! -f DEFAULTS_FILE` is always true, so the `tar` copy runs on every shell start. `tr < REQUIRED_FILE` errors when the file is missing.
- [x] **B6. pyenv/rbenv logic errors.** (1.2.3, 2026-10-26)
  - `:804` prints `RUBY_VER` in the pyenv section.
  - `:803`, `:811` say "local" but run `pyenv global`.
  - `:770` `rbenv local` writes `.ruby-version` into the current directory on every login.
  - `install --list` runs on every shell start (slow) and `grep | tail -1` is not a reliable "latest"; use `sort -V`.
  - `global` is set to a version that may not be installed when `DO_BUILD` is false.
- [x] **B7. Homebrew installer downloaded during dry-run** (1.2.4, 2026-10-26) (`:1117`). `$(curl ...)` expands before `execute_command` is called.
- [x] **B8. Package install problems.** (1.2.5, 2026-10-26)

## Performance / best practices

- [x] **P1. Startup cost.** (1.3.0 defaults stamp, 1.3.1 init cache, 1.3.2 fork-free shell work, 2026-10-26) Measured in a sandbox: 133 external processes and about 1390 ms per login down to 1 process (oh-my-posh) and about 70 ms, with init commands stubbed. Follow-ups: oh-my-posh init is not cached (its output embeds a per-run POSH_SESSION_ID, ~250 ms); applying defaults still forks `defaults read` per key (batch with one read per domain); zinit plugins load eagerly (see C7).
- [x] **P2. Quoting / injection.** (1.3.5, 2026-10-26) Unquoted paths in command strings and `eval` with embedded values. Done with `${(q)var}` at every interpolation (tested with a hostile home directory name). `zinit.zsh` lines run by `execute_from_file` are still evaluated as written, by design.
- [x] **P3. Zsh idioms.** (1.3.4, 2026-10-26; `[[ ]]` conversion 1.9.8, 2026-11-13) `typeset -U path`, `path+=`, `$commands` lookups. The 517 `[ ]` tests are `[[ ]]` now, checked by the full suite (1099 passed). Converted by a script, then reviewed for the two places the operators differ: no right-hand side of `=` is unquoted (so no pattern changes) and no `-a`/`-o` was used.
- [x] **P4. Argument parsing.** (1.3.6, 2026-10-26) `zparseopts -F` replaces the loop (also fixes `-g` with no value looping forever, and allows bundling like `-vt`). The small whole-argument pre-scan for `-F`/`-I`/`-v` stays because the lock and verbose output are needed before parsing.
- [x] **P5. Supply chain.** (1.3.7, 2026-10-26) Installers are downloaded then run, with an optional `*_INSTALL_SHA256` check; clones take an optional `*_REF` pin. Both are opt-in (pinning by default would stop rbenv/pyenv learning new versions, and there is no checksum that does not go stale). `--update` pinning is done in I1 (1.8.0): `SCRIPT_SHA256` and `UPDATE_SHA256` are checked when set, opt-in, so by default `--update` still follows the `main` branch. Decided against, not pending: `brew bundle` (a Brewfile needs the formula/cask/tap distinction the plain lists lack, and one failing package would no longer be isolated). Reviewed 2026-11-13; nothing left to do here unless the lists change shape.
- [x] **P6. `--confirm`.** (1.3.3, 2026-10-26) `vared` itself worked on a terminal and did not hang without one; the real bug was that the prompt did not show the command unless `--verbose`. Now `read` with the command in the prompt, and a visible warning when there is no terminal.
- [x] **P7. Maintenance.** (1.3.8, 2026-10-26) `have_lock`/`is_osx`/`is_linux`, `copy_support_files` and early returns in the package and defaults checks; `tests/smoke.zsh` (zsh, no extra dependencies) covers the fixes above.

## Plugin manager ideas (from the review of 2026-11-13)

- [ ] **S1. Static plugin bundle.** antidote-style: `--update` or the first login after a change compiles the plugin lists into one file under `~/.ussuri/`, and a login sources only that file. The zinit step is the largest startup cost (about 60 ms in the `--timing` runs), and most of it is resolving the lists at each login. Done when a steady login reads the bundle, falls back to the lists when the bundle is missing or older than the lists, and the `login_starts` test still passes. Turbo mode needs its deferred lines kept deferred in the bundle.
- [ ] **S2. Lock file for plugins.** Each plugin records the commit it is at in `~/.ussuri/plugins.lock`, written by `--update`, and login checks out those commits, so the same plugins load on every machine that uses the lock. Done when `--update` writes the lock, a login with a lock uses its commits, `--update --unlock` (or similar) moves a plugin forward, and `--doctor` warns when a plugin is not at its locked commit. Open question: zinit does not expose a per-plugin commit pin the way `*_REF` does for installers, so this may need `git -C` checks on each plugin directory.

- [ ] **S3. Starship as a prompt engine (for consideration).** A third value for `PROMPT_ENGINE` next to p10k and posh, so one config works in any shell. Starship has its own config file, so the top-line settings (`PROMPT_TOP_ELEMENTS` and the date) would need a Starship equivalent. Decide first whether the top line is worth keeping under Starship.
- [ ] **S4. Encrypted secrets in the dotfiles (for consideration).** chezmoi and yadm can encrypt files (age, GPG or git-crypt), so a token is not stored in plain text. `--export` bundles plain files only, so it would need the same encryption before it could carry a secret. Decide first which tool (age is the simplest to add with no keyring) and whether `--export` should ever carry secrets.
- [ ] **S5. Templated files per machine (for consideration).** chezmoi renders one template per machine (name, OS, hostname) rather than copying one file per layer. The profile and host layers already cover most of this by copying, so this would be a smaller change: a template syntax for the dotfiles, rendered at link time. Decide first whether the copy-per-layer model is enough.
- [ ] **S6. A recommended preset (for consideration).** zsh4humans gives a complete, tested setup in one step with few decisions. A `--preset recommended` (or a `PRESET=recommended` setting) that sets the usual choices in one place, leaving the switches for changes. Decide first which choices belong in the preset.
- [x] **S7. Turn plugins off by name (2.4.0, 2026-11-13).** Prezto lists each module with an on/off switch in one place. Ussuri has `!name` exclusions for packages, but plugins are only excluded by editing the layer files. A `PLUGIN_EXCLUDE` (or similar) list would match the package exclusions.
- [x] **S8. Averaged startup timing (2.3.0, 2026-11-13).** zsh-bench runs several logins and reports the average and spread, so one slow login does not mislead. `--timing` reports one login. A `--timing --runs N` mode that reports the median of N would give steadier numbers for S1 and S2 to be judged by.
- [x] **S9. `--selftest` (2.2.0, 2026-11-13).** Done as a plugin-list check, not a full login: it loads `zinit.zsh` in a temporary home and reports each line (ok, warn, fail or skip), so no login steps run. Originally: starts a throwaway login in a temporary home and reports what loaded, what failed and how long each step took, without touching the real home. It would catch a broken plugin before it reaches a real shell. `--doctor` is read-only and does not run a login, so it cannot do this.
